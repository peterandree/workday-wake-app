アラームの信頼性

Workday Wake が Xiaomi、Samsung、Huawei など積極的なバッテリー管理の 端末でも鳴り続けるよう設計されている仕組み — と、お使いの端末で確認できることを解説します。

このページの目的 · 敵対的な環境が実際にすること · 重ねてきた防御層 · 図解 · 端末内の診断 · 診断の共有 — 任意、あなたの裁量で · あなたが制御します · 正直な限界 · まとめ

このページの目的

素の Android 端末（例: Google Pixel）では、きちんと作られたアラームアプリは ほぼ問題なく動きます。しかし Android のインストール基盤の多くではそうはいきません。複数の メーカーは、バックグラウンドアプリを終了させ、スケジュール済みアラームを黙って破棄し、アプリの 自己再起動を阻む電源管理機能を搭載しています。しかも普通は 何かが取り消されたことをアプリに知らせる仕組みすらないのです。

本質的な問題はこの非対称性です: アラームは消えたのに、アプリは察知できない。 Workday Wake がこれに対して行うことはすべて、一つの問いを軸に設計されています: ある仕組みが消されたとき、どの別の仕組みがそれに気づくのか？

このページは、そのエンジニアリングの物語を一般向けに読みやすくした版です。こうした端末が 実際に何をするか、アプリがそれへどう応えるか、万一の際にアプリ内から診断を確認・共有する 方法を説明します。ブランド別の設定手順とアプリ内のガイドは同じ情報源から来ています。万一 このページとアプリが食い違った場合は、設定 > 信頼性 画面のほうが お使いの端末に関して確からしい情報です。

重ねてきた防御層

上記のどの UI も 1 つの仕組みではカバーできないため、Workday Wake は独立した 層を重ねています。それぞれの層は、前の層がすでに破壊されている可能性を想定しています:

予防目覚ましアラームは setAlarmClock() でスケジュールされます。Android が提供する最も優先度の高いアラーム API は Doze から免除され、システム時計の UI に表示され、プロセスが死んでいても配信されます。 それがステータスバーに小さなアラームアイコンを出す理由でもあります。バグではなく、 アプリが動いている証拠です。
復元アラームは再起動後、 タイムゾーン変更後、アプリ起動のたび、そして定期オフライン保守ジョブによって 再登録されます（正確なアラームの権限は 8 時間ごとに確認）。これらのジョブは プロセスの生存に依存しないため、OEM に消されたものをすべて再設定できます。
監視必要な端末では、小さな第二プロセスが 6 時間ごとに主プロセスへ通信します。どちらかの側が 13 時間 沈黙したら、もう一方がアラームを再設定します。この層は既定では オフ（メモリを消費）。 既知の挙動を持つブランドや、初めて記録された信頼性インシデントの後には自動でオンになり、 その後黙ってオフに戻ることは決してありません。
検知・修復全アラームが鳴る予定の時刻を記録し、 実際の ringing は実際に鳴ったことを記録します。予定されていたアラームが鳴らない場合、アプリは ミスをカウントし、アラーム一覧と同じ情報源から黙って再スケジュールします — あなたが眠っている間でもです。
正直にエスカレーション検知自体が壊れているように見える場合 （あるガードが 3 回連続で沈黙している場合）、アプリは「アラームの信頼性が 低下している」という一本の目立つ通知を出します。すべて問題ないと装うのではなく。

ある層が前の層の失敗を拾うためだけに存在するなら、 それがその層の仕事です — ミス、自己修復、エスカレーションは記録され、隠されません。

層の図解

これらの図はエンジニアリング・ドキュメントから直接レンダリングされています。 実装と並行して手作業で管理されており、信頼性の設計自体が変わったときにのみ変更されます。

メーカー別の設定手順（アプリ内ガイドより）

アプリには対象端末向けの内蔵ガイド（設定 > 信頼性）があり、メーカーごとの 正確な手順を収録しています。主要なものを簡潔に — 設定内でアプリ名が出る箇所は “Workday Wake” をランチャー内のアプリ名に置き換えてください:

ブランド / UI手順（アプリの端末バッテリーガイドと同じ）
Xiaomi / MIUI, HyperOSAutostart を許可；高度な権限で「ロック画面に表示」と 「バックグラウンド実行中にポップアップウィンドウを表示」を有効化；アプリ > 省電力を 「制限なし」に；最近使ったアプリでロック（下スワイプまたは錠前）。
Samsung / One UI設定 > バッテリーとデバイスケア > バッテリー > バックグラウンド 使用制限：「スリープ状態のアプリ」「深いスリープ状態のアプリ」から削除し 「スリープ状態にしないアプリ」へ追加；設定 > アプリ > Workday Wake > バッテリー > 制限なし。 「未使用アプリをスリープ状態にする」がオフになっているか確認 — 数日未使用のアプリの アラームを抑圧することがあります。
Huawei / EMUI, HarmonyOS設定 > バッテリー > アプリ起動：「手動で管理」にし、 自動起動・二次起動・バックグラウンド実行を許可；バッテリー最適化：「許可しない」。
OnePlus / Oppo / Realme (ColorOS)バッテリー最適化：「未最適化」；アプリ情報 > バッテリー：「バックグラウンド アクティビティを許可」／「制限なし」；起動マネージャーで 自動起動を許可；DuraSpeed の監視リストから Workday Wake を外す。
Vivo / iQOO権限マネージャーで自動起動を許可；バッテリー最適化を無効化； バックグラウンド アクティビティを許可し、最近使ったアプリでロック。
Sony設定 > バッテリー > STAMINA モード：「オフ」— または追加制限の 「バッテリー時間を優先」をオフに。

他のファミリー（Asus PowerMaster、Meizu、Lenovo、Motorola Battery care、Nokia DuraSpeed、Transsion/itel/Infinix の Phone Master）も、アプリ内で同じ扱いを受けます: 設定 > 信頼性 がメーカーを検出し、お使いの端末に当てはまる手順だけを表示します。 すべての手順はアプリ内に恒久的な文字列リソースとして存在します；ハードコードや ブランド固有の分岐はありません。

ほぼすべての UI で効くプロの小技: 最近使ったアプリを開き、Workday Wake を ロックしてください（錠前アイコン）。この一手でスワイプによる強制終了と メモリクリーナーによる損失の大半を防げ、スキップをタップした後に更新が止まる ウィジェットも直ります。

端末内の診断

上記の信頼性エンジニアリングはどれも、端末内で確認できる痕跡を残します。 設定 > 診断 では、バグ報告が尋ねるのと同じ質問にアプリが答えます:

  • ウェブ側: 監視ハートビートは打たれているか？アラームが最後に スケジュールされた いつか、鳴る予定だったとき、実際に鳴ったときは？
  • ミスは何回検知されたか、最後に 自己修復（ミス後の再スケジュール）したのはいつか？
  • アプリのバージョン、Android のバージョン、メーカーと機種 — メーカー固有の 挙動が実際に存在する場所です。
この画面の内容はすべて端末上で計算・保存されます。診断は送信機ではなく 鏡です: アプリにはそれを自分でアップロードする手段がありません。

設定 > 信頼性 では、お使いの端末の保護階層（「Tier 1 / Tier 2」）、カウントされた ミスの数、そして該当ブランドの端末バッテリーガイドそのものも見られます。

診断の共有 — 任意、あなたの裁量で

アラームが失敗し助けが必要な場合、設定 > 診断 には 「開発者へ送る」アクションがあります:

  1. オプトインです: 何かが起こる前に、ダイアログですべてのフィールドを一覧表示します。
  2. レポートは技術情報のみ — タイムスタンプ、カウンター、バージョン、メーカー/機種。 アラームのラベル、名前、識別子は一切含みません。
  3. 送り先はあなたが選びます（メール、メッセンジャー、共有シート対応の何でも）。 ドラフトで送信を押さない限り、端末からは何も出ません。
アプリのどこにもアップロード先、クラッシュレポートサービス、自動バックグラウンド送信は ありません。共有シートをまったく使いたくない場合のためのクリップボード代替もあります。

あなたが制御します

  • アカウントなし、分析なし、広告なし — 信頼性エンジニアリングは 端末内のリソースだけで行われます。プライバシーポリシーをご覧ください。
  • Alarm Guard: アプリを生かし続ける常駐通知サービスは 設定 > 信頼性 でオフにできます（制限の厳しい端末ではアラームミスに対する保護が 若干下がります）。
  • Tier 2 監視 は既知のブランド一致か記録済みインシデントの後にのみ 追加コンポーネントを有効化します。隠れた報告チャネルはありません。
  • アンインストールまたはアプリのストレージ消去は完全なリセットです: すべての診断カウンター、ハートビートのタイムスタンプ、アラームミスの記録は お使いの端末のアプリストレージにのみ存在します。

正直な限界

  • AOSP の基盤で検証されており、全部の端末ではありません。 耐性設計は スローアウェイの Pixel AVD で、AOSP（Android Open Source Project）の 原始操作（プロセス強制終了、ディープ Doze、スタンドアロンバケット）でテストされています。 自動化できるのはそこまでだからです。エミュレーターは Xiaomi Autostart ゲート、 Samsung Device Care、OEM のアラームスロットリングを完全に再現できません — 実機の挙動は dontkillmyapp.com の情報、ブランド別レポート、そしてあなたのようなユーザーが 送る診断情報で拾っていきます。
  • 保証はありません。 積極的な OEM はファームウェアのバージョン間で 電源管理を変えます。ブランドが新しい kill 機構を導入した場合、対応にはアプリの 更新が必要になるかもしれません。それを見つけるのが診断情報です。
  • ステータスバーのアラームアイコンは意図的なものです — アラームに最適な スケジュール API が伴います。
  • iOS 版は存在しません。 上記のエンジニアリングは Android の API （契約ベースのアラーム、WorkManager、正確なアラーム権限）に依存しており、iOS には 比較可能な同等物がありません。

まとめ

目覚まし時計の仕事は一つです。Workday Wake は最初から、その仕事の最も過酷な形を想定して 設計されています: プロセスの死をかいくぐるスケジューリング、消されたものの再設定、 必要な場合の第二プロセスによる自己監視、そして問題が起きたときの端末内での正直な報告。 そしてプライバシーの線は絶対です — その正直さがデータを犠牲にすることはありません。

このガイドが当てはまらない端末を見つけましたか？ issue を立てて、 可能であれば任意の共有アクション経由で端末の診断を添えてください。このフィードバックの 環は、エミュレーターでは代替できない唯一つのものです。
